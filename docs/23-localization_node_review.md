## 0. 무엇을 받았나

localization 팀이 우리 `/odom` 명세에 맞춰 새로 붙인 버전이다.

- 기존 `/localization/state`(그쪽 MPC 전용, 20Hz)는 **그대로 유지**
- 마스터 타이머를 `/odom` 주기(40Hz)로 돌리고 `publish_every_n_ = 2` 로 나눠서 20Hz 를 보존 — 검증된 MPC 튜닝을 안 건드리는 방식이라 구조는 깔끔하다
- dead-reckoning 이중적분 버그를 같은 날 수정한 흔적이 주석에 있음 (488~502행)

우리 워크스페이스에선 빌드되지 않는다. `autonomous_driving/LocalizationState.h` 를 참조하는데 그건 그쪽 패키지다. 정상.

## 2. [최우선] 좌표 프레임 정합

**우리 경로 CSV 는 MORAI 맵 로컬좌표다.** `path_smooth.csv` 첫 줄이 `x≈-13.97, y≈-223.67, z≈28.82` 이고, 이건 `path_recorder.py` 가 `/ego_status` 의 position 을 그대로 기록한 값이다.

**그쪽 `/odom` 은 다른 방식으로 만들어진다.** `latlonToLocal()`(56~66행)은 `origin_file` 의 lat0/lon0 를 기준으로 한 **구면 근사(equirectangular)** 다.

```cpp
x = (lon_rad - lon0_rad) * cos(lat0_rad) * kEarthRadius;
y = (lat_rad  - lat0_rad) * kEarthRadius;
```

이 둘이 같은 프레임이라는 보장이 없다.

- `morai_msgs/GPSMessage` 에는 `eastOffset` / `northOffset` 필드가 있고, 주석이 *"East/North offset from map origin [m]"* 다. 맵 원점 정렬용으로 존재하는 필드인데 **그쪽 코드는 이 두 필드를 아예 읽지 않는다.**
- **우리 브릿지는 이 값을 0.0 으로 발행한다** (`udp_bridge.py:356-357`). 배선 누락이 아니라 UDP 로 오는 NMEA 텍스트에 그 정보가 없기 때문이다 — 7.8절 참조.
- 원점을 맞춰도 투영 방식이 다르면 스케일·회전 차이가 코스 전 구간에 걸쳐 남는다. 코스가 수백 m 규모라 무시할 수 있다고 단정할 수 없다.

### 검증 결과

## 3. `twist.linear.x` 가 `/ego_status` 유래

`ref_vx_` 는 `/ego_status` 에서 온다(467~475행). km/h → m/s 변환은 제대로 했다(`/3.6`).

**문제는 `has_fix` 에 `has_ref_vx_` 가 빠져 있는 것이다** (486행, 504행).

```cpp
bool has_fix = has_gps_ && has_imu_;      // has_ref_vx_ 가 없다
...
if (has_fix && has_ref_vx_) { /* dead-reckoning */ }
...
if (has_fix) { odom.twist.twist.linear.x = ref_vx_; /* 0.0 인 채로 */ }
```

`/ego_status` 가 안 오면:

1. dead-reckoning 이 통째로 꺼진다
2. `/odom` 은 **`twist.linear.x = 0.0` 으로 조용히 계속 발행된다.** 경고 로그도 없다

즉 명세 (c) "GPS 음영구역 연속성" 이 **IMU 추측항법이 아니라 `/ego_status` 에 의존**하고 있다.

### 영향

- **지금은 무관.** 우리 planning 은 전부 `/ego_status` 를 직접 구독한다 (`acc_planner.cpp:64`, `lattice_planner.cpp:41`, `path_tracker.py:130`).
- **WBS 7.1 로 `/odom` 교체하는 순간 문제가 된다.** `twist.linear.x = 0` 이 ACC 에 "정지 중" 으로 들어간다.

### 규정 측면

9109(Competition Vehicle Status)에서도 velocity 가 나온다면 합법이다 (`04-runbook.md` 상 9109 는 position 만 0,0,0). 다만 그러면 **localization 이 우리 브릿지 토픽에 의존하는 구조**가 된다. 명세에 명시하든가, 그쪽이 자체 소스를 쓰든가 정해야 한다.

## 4. `gps_blend_alpha_ = 1.0` 하드스냅

```cpp
ego_x_ = gps_blend_alpha_ * x + (1.0 - gps_blend_alpha_) * ego_x_;   // alpha=1.0 → 그냥 덮어씀
```

448~449행, 기본값 605행. GPS(실측 6~8Hz)가 올 때마다 위치를 그 순간 값으로 **덮어쓴다.** `/odom` 은 40Hz 니까 DR 오차만큼의 톱니가 그대로 나간다.

`51-traffic_light_brief.md` 2절에 "최근접 waypoint 탐색이 제일 중요하다" 고 적어둔 그 지점을 정통으로 때린다. DR 이중적분 버그를 고쳐서 진폭은 줄었을 것이나, 2절 실측할 때 같이 본다.

# 7. 실측 결과 (2026-08-03)

2절에서 "미검증, 최대 리스크" 로 남겨둔 좌표 프레임 정합을 실측했다.

**결론: 현재 변환 방식으로는 최대 11.3m 어긋난다.** 원인 세 가지를 모두 특정했다.

> 이 절은 **증상과 원인까지만** 적는다. 해결 방식은 localization 팀의 판단 영역이다.

## 7.1 측정 방법

`/odom` 을 직접 띄우지 않았다. `autonomous_driving` 패키지가 우리 쪽에 없기도 하고,
애초에 물어야 할 질문이 "**GPS 위경도와 MORAI 맵 좌표가 같은 프레임인가**" 라서
그쪽 노드 없이도 답할 수 있다.

- `diag_frame.py`(신규) 로 `/gps` 와 `/ego_status` 를 **원시 그대로** 각각 CSV 에 기록
- 한 바퀴 주행 (300.5초, 2840.6m — 경로 2830m 와 일치하므로 완주)
- ego 26.0Hz / gps 6.2Hz. 주기가 다르므로 **노드에서 짝짓지 않았다**.
  55km/h 에서 50ms 어긋나면 0.76m 인데, 이는 우리가 재려는 값과 같은 크기다.
  분석 단계에서 ego 위치를 GPS 시각으로 보간해 이 오차를 제거했다
- 좌표가 실제로 갱신된 표본만 사용 → **1281 쌍**

재현: `scripts/diag_frame.py` + `scripts/analyze_frame.py`.
로그는 `catkin_ws/logs/frame_{gps,ego}_frame.csv` (gitignore 대상).

## 7.2 결과

두 좌표계를 겹치는 데 무엇이 필요한지 단계적으로 시험했다.

| 맞추는 방식 | 잔차 RMS | 최대 |
|---|---|---|
| **평행이동만** (= 현재 `origin_file` 방식) | **6.60 m** | **11.34 m** |
| 회전 + 축척 + 평행이동 | 1.77 m | 3.08 m |

원점만 맞추는 것으로는 정합이 성립하지 않는다.

## 7.3 원인 ① — 두 좌표계가 1.26° 비틀려 있다

회전을 허용하자 잔차가 6.60m → 1.77m 로 떨어졌다. 측정된 회전각은 **−1.2595°**.

이 값의 정체는 **UTM 격자수렴각**이다.

| | 값 |
|---|---|
| 측정된 회전 | **−1.2595°** |
| UTM 52N 격자수렴각 이론값 (중앙자오선 129°E, K-City 126.774°E) | **−1.3476°** |

UTM 은 지구를 세로 60조각으로 나눠 각각 평면에 편다. 조각의 중앙자오선 위에서만
격자북과 진북이 일치하고, 동서로 벗어날수록 어긋난다. K-City 는 중앙자오선에서
서쪽으로 2.23° 떨어져 있다.

→ **MORAI 맵 로컬좌표는 UTM 기반이다.** `morai_msgs/GPSMessage` 에
`eastOffset`/`northOffset`("offset from map origin") 이 있는 것도 이와 부합한다.

→ 현재 `latlonToLocal()`(56~66행)은 UTM 이 아니라 **원점 기준 구면 근사**다.
이 불일치가 회전의 원인이다.

(측정 −1.2595° 와 이론 −1.3476° 의 0.09° 차이는, 등방(等方) 축척 하나로 맞추도록
강제한 탓이다. 실제 오차는 남북/동서가 다른 이방성이라 일부가 회전으로 새어든다.)

## 7.4 원인 ② — 축척이 2837ppm 작다

| | 값 |
|---|---|
| 측정된 축척 | 0.997163 (**−2837 ppm**) |
| 타원체 자오선반지름 M / 구형반지름 | 0.996970 (**−3030 ppm**) |
| 타원체 묘유선반지름 N / 구형반지름 | 1.001228 (+1228 ppm) |

`latlonToLocal()` 은 남북·동서 **양쪽에 적도반지름 6,378,137m** 를 쓴다.

```cpp
x = (lon_rad - lon0_rad) * std::cos(lat0_rad) * kEarthRadius;
y = (lat_rad  - lat0_rad) * kEarthRadius;
```

지구는 회전타원체라 위도 37.24° 에서 자오선반지름은 **6,358,810m** 다. 구형 가정이
원인이며, 남북과 동서의 필요 반지름이 서로 달라 **단일 축척으로는 애초에 맞출 수 없다**.

크기: **1km 당 −2.84m**. 코스가 2.8km 이므로 무시할 수 없다.

**주의 — 이 오차는 시간에 따라 누적되지 않는다.** 원점에서의 거리에 비례하며,
원점으로 돌아오면 사라진다. dead-reckoning 표류(진짜 누적)와는 성격이 다르다.

## 7.5 원인 ③ — GPS 안테나가 차량 기준점에서 앞·위로 떨어져 있다

회전·축척을 보정하고도 1.77m 가 남았다. 잔차를 **차체 좌표로 회전**시켜 보면:

```
잔차 평균(차체기준)   전방 −1.651 m / 좌측 +0.179 m
크기 1.661 m  =  잔차 RMS 1.772 m 의 94%
```

잔차는 `ego − GPS` 이므로, 이 값은 **GPS 가 차량 기준점보다 1.65m 앞에 있다**는 뜻이다.
차량 진행 방향과 무관하게 일정하며, 남은 오차의 대부분이 이것이다.

**시각 동기 오차가 아니라는 근거** — 속도로 나눠 보면:

| 구간 | 표본 | 잔차 RMS |
|---|---|---|
| 저속 (<5) | 9 | 1.94 m |
| 고속 (>30) | 1210 | 1.76 m |

동기 오차라면 고속에서 훨씬 커야 한다. 속도와 무관하므로 **정지 상태에서도 존재하는
물리적 거리**다.

고도도 부합한다. GPS altitude 29.6~30.1m vs ego z 28.4~28.9m → 약 **1.16m 위**.

### 교차 검증 — 시뮬 센서 설정값과 대조

MORAI 센서 설정창의 GPS 장착 좌표를 확인한 결과 **`(1.9, 0, 1.2)`** 였다.

| 축 | 설정값 | 실측 | 차이 |
|---|---|---|---|
| 전방 | +1.9 | +1.65 | 0.25 |
| 좌측 | 0 | +0.18 | 0.18 |
| 상방 | +1.2 | +1.16 | **0.04** |

**z 만 유독 정확한 것이 핵심이다.** 좌표 정합은 x, y 만으로 맞췄고 z 는 계산에
넣지 않았다. 따라서 z 는 보정 과정을 거치지 않은 순수 측정값이라 설정값과 그대로 맞는다.

x, y 는 평행이동 항을 최소제곱으로 맞추는 과정에서 **일부가 흡수된다**. 주행 중
차량 heading 분포가 균일하지 않으면(도로 코스이므로 당연히 불균일) 차체 고정
오프셋의 일부가 "지도 전체를 미는 값" 으로 빨려 들어간다. 그래서 1.9 의 87% 인
1.65 만 남았다.

→ **설정값이 참값이고 실측은 과소평가다.** 회전·축척은 이 흡수와 무관한 성분이므로
영향받지 않는다. 세 축의 부호와 크기가 모두 부합하므로 **본 분석 전체가 독립 검증되었다.**

**→ 2026-08-03 결정: 센서 장착 위치는 대회 규정상 팀 자율이므로, GPS 를 차량 기준점
(0,0,0)으로 옮겨 이 오차를 원천 제거한다.** 코드 보정은 하지 않는다.

- 옮기기 전에 MORAI 센서 설정창의 현재 장착 좌표를 기록할 것.
  실측 1.65m/1.16m 와 일치하면 본 분석 전체(회전·축척 포함)가 독립 검증된다.
  불일치하면 센서 장착 기준점과 `/ego_status.position` 기준점이 다르다는 뜻이므로
  그것부터 규명해야 한다.
- 적용 후 `diag_frame.py` 로 재측정. 안테나 항이 0 근처로 가고 **회전·축척은 그대로여야**
  한다(센서 위치와 무관한 값이므로). 변하면 모델이 틀린 것이다.
- 설정값은 세 팀이 동일해야 한다. 한 팀만 옮기면 그 팀 데이터만 달라진다.

## 7.6 남는 오차 0.62m — 이것이 바닥값이다

세 원인을 모두 보정하면 잔차 RMS **0.618m**, 최대 1.486m.

GPS 좌표 양자화(7.7절)만으로 설명되는 몫은 0.08m 에 불과하다. 나머지는 대회 규정의
**"GPS/IMU 노이즈 인가됨"**(`01-competition_rules.md`) 그것으로 보인다.

**planning 쪽 함의**: `lap_logger.py` 의 위험 판정 기준이 0.654m(차로 3.2m − 차폭
1.892m 의 편도 여유)다. **GPS 노이즈 바닥값이 그 여유를 거의 다 먹는다.**
`/ego_status` → `/odom` 전환 시 현재 CTE 튜닝 마진이 사라진다는 뜻이다.

## 7.7 부수 관측 — GPS 갱신 주기와 양자화

**갱신 주기가 규정집과 다르다.**

| | 값 |
|---|---|
| 규정집 명시 | 30Hz |
| 브릿지 발행 실측 | 6.2Hz |
| 좌표가 실제로 바뀌는 주기 | **약 4.3Hz** (측위 간격 0.17~0.23s) |

**좌표가 0.185m 격자로 양자화되어 있다.**

MORAI 가 UDP 로 보내는 것은 **NMEA 0183 텍스트**(`GPRMC`/`GPGGA`)다. 위경도가
`ddmm.mmmm` 형식이라 분(minute) 소수점 4자리가 표현 한계다.

```
0.0001분 ÷ 60 = 0.000001667 deg
실측 최소 변화량 = 0.000001666 deg      ← 일치
고유값 1119개 전부 이 격자 위에 존재
```

미터 환산: **위도 방향 0.185m / 경도 방향 0.148m** (경도는 cos(37.24°) 만큼 짧다).

브릿지는 문자열에 있는 자릿수를 그대로 파싱한다(`_nmea_to_deg`). 즉 **정밀도는
브릿지 도달 전에 이미 결정되어 있다.** 고도도 GPGGA 소수점 1자리라 0.1m 계단이다
(고유값 6개: 29.6~30.1).

**vy 추정에 대한 함의**: 현재 `gpsCallback` 은 GPS 위치를 미분해 횡속도를 얻는다.
0.185m 격자를 6.2Hz 로 미분하면 **약 1.15 m/s** 의 양자화 잡음이 생긴다.
`vy_clamp_ = 2.0` 과 LPF 가 필요했던 배경으로 보인다.
(다만 GPS 노이즈 0.62m 를 미분한 몫이 ~3.8 m/s 로 이보다 크다.)

**[우리 쪽 문제] 브릿지가 같은 측위를 두 번 발행하고 있다.**

`udp_bridge.py` 의 GPS 수신부는 `GPRMC` 와 `GPGGA` **양쪽 모두**에서 발행 콜백을
호출한다. 두 문장은 같은 측위를 형식만 달리 담는다. 게다가 UDP 패킷 하나에 두 문장이
함께 오면 한 패킷에 두 번 발행된다.

```
연속 메시지 간격 0.00초대  508건   ← 같은 패킷에서 연달아 나온 것
좌표가 이전과 완전히 동일  586/1867 (31%), 평균 간격 0.029초
```

이 중복은 `gpsCallback` 의 `dt > 1e-3` 가드를 **통과한다**(0.029초 > 0.001초).
위치가 안 변했으므로 `dx=dy=0` → `raw_vy = 0` 이 되어, **GPS 콜백 3번 중 1번꼴로
횡속도 추정에 0 이 주입된다.**

**이건 브릿지 쪽 문제이므로 localization 쪽 조치는 필요 없다.**
(브릿지는 별도 담당자 소유. 진단·로그·검증 방법은 planning 이 전달한다.)

단순 dedup 은 함정이 있다 — 정지 중에는 좌표가 실제로 변하지 않으므로, 중복으로 보고
거르면 GPS 가 끊긴 것처럼 보인다. **UDP 패킷 하나당 최대 한 번 발행**이 안전하다.

## 7.8 정리 — localization 팀에 전달할 것

| # | 증상 | 원인 |
|---|---|---|
| 1 | 원점만 맞추면 최대 11.3m 어긋남 | 좌표계가 1.26° 비틀려 있음. MORAI 맵은 UTM 기반인데 `latlonToLocal()` 은 UTM 이 아님 |
| 2 | 축척 −2837ppm (1km 당 −2.84m) | 구형 가정. 남북·동서 모두 적도반지름 사용. 위도 37.24° 의 자오선반지름과 −3030ppm 차이 |
| 3 | 위 둘 보정 후에도 1.65m 상수 오차 | GPS 안테나가 차량 기준점보다 앞·위로 떨어져 있음 (시뮬 설정 실측 `1.9, 0, 1.2`) |
| 4 | (정보) 보정 후 잔차 0.62m | 대회가 인가하는 GPS 노이즈. 제거 불가한 바닥값 |
| 5 | (정보) GPS 4.3Hz, 0.185m 격자 | NMEA `ddmm.mmmm` 형식의 표현 한계 |

1~3 은 **동시에 존재하며 서로 독립**이다. 하나만 고쳐서는 11.3m 가 크게 줄지 않는다.

### ⚠️ 함께 전달할 제약 — `eastOffset`/`northOffset` 은 `/gps` 로 오지 않는다

원인 ① 을 다룰 때 반드시 먼저 알아야 하는 사항이다.

`morai_msgs/GPSMessage` 에는 `eastOffset`/`northOffset`(맵 원점 오프셋) 필드가 있지만,
**우리가 발행하는 `/gps` 에는 항상 0 이 들어간다.**

```python
# udp_bridge.py:356-357
out.eastOffset = 0.0
out.northOffset = 0.0
```

이는 배선 누락이 아니다. 대회 규정상 GPS 는 UDP 로 받아야 하고, MORAI 가 그 포트로
보내는 것은 **NMEA 0183 표준 텍스트**다. NMEA 는 전 세계 공용 GPS 형식이라
위경도·고도·시각·위성수만 담는다. "이 시뮬레이터 맵의 원점이 UTM 어디인가" 같은
시뮬 고유 정보는 **애초에 담길 자리가 없다**.

`GPSMessage` 에 그 필드가 존재하는 것은 MORAI **자체 ROS 브릿지**가 시뮬 내부에서
값을 채워주기 때문이며, UDP 경로에는 그 통로가 없다.

→ **맵 원점 값은 `/gps` 이외의 경로로 확보해야 한다.** 어떤 경로를 쓸지는
localization 팀 판단 영역이나, 이 제약을 모른 채 시작하면 변환을 다 구현하고도
원점에서 막힌다.

참고로 planning 은 이 실측 데이터(1281 쌍)를 보유하고 있다. 필요하면 제공 가능하다.
