## 1. 목적과 범위

ACC가 **종방향(속도)** 을 담당하듯, lattice는 **횡방향(조향 회피)** 을 담당한다. 경로 위 장애물을 좌우로 벌린 후보경로들을 그려 충돌검사하고, 안전하면서 비용 최소인 후보를 골라 회피 지역경로를 만든다.

### 담당 범위
- **정적장애물·NPC·보행자 회피**(횡): 경로 위 장애물을 좌우로 우회
- **차선변경성 기동**: 좌우 offset 후보로 자연스러운 우회
- 못 피하는 경우(전 후보 충돌)는 **경고만** 내고 정지는 ACC/behavior에 위임

### 범위 밖
- **종방향 속도 제어**: ACC 몫 ([40-acc_design.md](40-acc_design.md))
- **정지 판단**: 다 막혔을 때 실제 정지는 ACC/behavior FSM
- **시간축 궤적·동적장애물 예측**: FOT(stretch goal, [03-fot_theory.md](03-fot_theory.md))

## 2. 아키텍처

ACC와 대칭인 **순수 planning 노드**. `/ctrl_cmd`는 건드리지 않는다.

```
                    /Object_topic (perception, 지금은 mock)
                         │
  /local_path ──┐        │
  /ego_status ──┼──▶ [ lattice_planner.cpp ] ──▶ /lattice_path (nav_msgs/Path)  → 제어 추종
                │    (C++, path_tracking 패키지)  └▶ /lattice_candidates (MarkerArray) → RViz
                └────────┘
```

- 노드: `path_tracking/src/lattice_planner.cpp` (30Hz 타이머)
- 출력 `/lattice_path` = 횡방향 의도(회피 지역경로). ACC의 `/target_velocity`와 짝을 이뤄 control이 둘 다 소비.
- 회피 불필요 시 `/local_path`를 그대로 통과발행(오버헤드 최소화).

## 3. 데이터 흐름 & 로직 (30Hz `run()`)

```
① gatherObstacles   장애물을 원(중심+반경)으로 수집
                    트리거용은 npc+정적, 충돌검사용은 여기에 보행자까지
② objectOnPath      경로 위 장애물 있나? 없으면 local_path 그대로 발행하고 종료
③ generateCandidates 후보경로 생성 (좌표변환 + 3차곡선 + offset 유지 tail)
④ selectLane        각 후보 충돌검사 → 비용 계산 → 최소비용 argmin 선택
⑤ publish           선택 경로 → /lattice_path, 후보 전체 → /lattice_candidates
```

### 3.1 장애물 모델 (gatherObstacles)
- **보행자는 회피 트리거에서 제외한다**(`gatherObstacles(false)`). 미션이 횡단보도로
  신호를 위반하며 뛰어드는 사람이라, 옆으로 꺾으면 사람이 뛰어든 쪽이나 반대 차로로
  들어갈 수 있다. **보행자는 피하는 대상이 아니라 서는 대상**이고 그건 behavior/ACC 몫이다.
  단 다른 이유로 이미 회피 중일 때 보행자를 뚫고 가면 안 되므로 **후보 충돌검사에는
  포함**한다(`gatherObstacles(true)`).
- `npc_list + obstacle_list` (+ 충돌검사 시 `pedestrian_list`)
- 각 객체 → **원**: 반경 `r = 0.5 * max(size.x, size.y)`, 최소 0.3m
- 원 근사 → 충돌검사가 `거리 < 반경합`으로 단순

### 3.2 회피 트리거 (objectOnPath)
- 경로 점 × 장애물 원이 `d < r + CAR_HALF_WIDTH + SAFE_MARGIN` 이면 "회피 필요"
- 없으면 lattice 생략(비용 절감)

### 3.3 후보경로 생성 (generateCandidates) — 핵심
- **좌표변환**: local_path 시작점 + 진행방향 `theta`로 world↔local 프레임 정의. 후보를 차 진행방향 기준 local에서 그린 뒤 world로 복귀.
- **횡 offset**(`LANE_OFFSET`)마다 시작 횡위치(현재 차) → 끝 횡위치(offset)로 **부드럽게 잇는 3차곡선**:
  - 경계조건: `y(0)=ps, y'(0)=0, y(xf)=pf, y'(xf)=0` (시작·끝 기울기 0 → 부드러운 진입/복귀)
  - 계수: `a0=ps, a1=0, a2=3(pf-ps)/xf², a3=-2(pf-ps)/xf³`
- **전이 길이 `xf` 는 거리가 아니라 시간으로 정한다.** 6.1 참고.
- 후보 뒤쪽(tail)은 기준경로를 따라 연장하되 **법선 방향으로 offset 을 유지**한다. 3.5 참고.
- 상세 유도는 [31-lattice_code_review.md](31-lattice_code_review.md)

### 3.4 후보 선택 (selectLane)
- 비용 = `BASE_WEIGHT` + 충돌 시 `COLLISION_PENALTY(100)`
- `argmin(weight)` 선택 → **충돌을 면하는 가장 작은 회피**
- ⚠️ **벌점은 후보당 한 번만 준다.** 예전에는 `break` 가 안쪽(장애물) 루프만 끊고
  바깥(점) 루프는 계속 돌아 충돌한 waypoint 개수만큼 +100 이 누적됐다. 장애물
  하나인데 가중치가 900, 800, 600 씩 붙었다. 그러면 "충돌하느냐" 가 아니라
  "몇 점이나 충돌하느냐" 로 순위가 매겨지고, 중앙선 회피 같은 기본 비용(20)이
  수백 점 벌점 앞에서 무의미해진다. (2026-07-31 수정)

### 3.5 tail 의 offset 유지
예전에는 tail 에 기준경로 원본 점을 그대로 붙여 offset 이 0 으로 되돌아갔다.
전이 길이가 24m 로 길던 시절에는 tail 이 장애물보다 뒤에서 시작해 무해했지만,
전이 길이를 속도 비례로 바꾸면서 저속에서 15m 로 짧아졌다. 그러면 tail 이 장애물
바로 위에서 시작해 **애써 비켜난 경로가 그 자리에서 원래 차선으로 되돌아간다**.
회피가 무효가 된다. 지금은 경로 접선의 법선 방향으로 offset 만큼 밀어서 붙인다.
- **전 후보 충돌** 시 `ROS_WARN_THROTTLE`("다 막힘 - ACC/behavior 정지 필요")

## 6. 설계 근거 (2026-07-31 실측·재설계)

### 6.1 전이 길이는 거리가 아니라 시간

옆으로 `D` 만큼 옮기는 데 앞으로 쓰는 거리를 `xf` 라 하자. 3차곡선의 최대 곡률은
`6D/xf^2` 이고 횡가속도는 거기에 `v^2` 를 곱한 값이다. 이를 `LAT_ACCEL_LIMIT`
이하로 두면

```
xf = v * T,     T = sqrt(6D / a)
```

가 되어 **속도가 상쇄되고 시간만 남는다.** `D=3.51m, a=2.94` 에서 `T=2.68초` 다.

| 속도 | xf | 횡가속도 |
|---|---|---|
| 20 km/h | 14.9m | 0.30G |
| 40 km/h | 29.7m | 0.30G |
| 55 km/h | 40.9m | 0.30G |

**예전 코드의 문제.** `look = v_kmh*0.4; if (look < 20) look = 20; end_idx = look*2`
로 waypoint 개수를 세었다. 하한 20 이 50km/h 이하를 전부 덮어써서 주행의 절반이
40점(약 24m)에 고정됐다. 완주 로그 기준 대회구간 샘플의 50.5% 가 50km/h 미만이다.
거리를 고정하면 시간이 속도에 따라 널뛴다.

| 속도 | 예전 xf | 걸리는 시간 | 횡가속도 | 증상 |
|---|---|---|---|---|
| 20 km/h | 24m | 4.3초 | 0.12G | 너무 느긋해 15m 앞 상자에 2.40m 밖에 못 비켜남(2.45m 필요) |
| 55 km/h | 26m | 1.6초 | **0.72G** | 한계의 2.4배. 차가 못 따라가고 밀려남 |

끝점은 **누적 거리**로 찾는다. 개수로 세면 경로를 다시 따서 waypoint 간격이
달라질 때 거동이 조용히 바뀐다.

`MIN_TRANSITION`(8m)은 정지 상태에서 후보가 하나도 안 생기는 것을 막는 하한이다.
8m 를 넘는 시점이 약 11km/h 이므로 주행 영역은 전부 시간 기준이 지배한다.

`LAT_ACCEL_LIMIT` 0.3G 는 타이어 한계(마른 아스팔트 약 1G)가 아니라 ACC 곡률
제한에서 이미 쓰고 있는 승차감·안전 기준이다. 새 기준을 만든 것이 아니라 같은
기준을 여기에도 적용한 것이다.

### 6.2 차로 폭과 후보 집합

**차로 폭 3.51m 는 시뮬 실측이다.** 직선구간(곡률반경 39928m)에서 차선 두 줄의
좌표 `(72.85,-55.36)` / `(69.34,-55.44)` 를 찍어 도로 수직 성분을 계산했다.
baseline 을 어떻게 잡아도 3.510m 로 일정했고(편차 0.001m) 종방향으로 어긋난
양도 0.060m 뿐이었다. 한국 고속도로 표준 3.5m 와도 맞는다.

차선 내 여유는 편도 `(3.51 - 1.892)/2 = 0.809m` 다.

**후보 집합을 바꾼 이유.** 예전 `{-3.0,-1.75,-1.0,1.0,1.75,3.0}` + `{3,2,1,1,2,3}`
은 세 가지가 잘못이었다.

1. **0 후보가 없었다.** `objectOnPath()` 가 걸리기만 하면 무조건 1m 이상 움직였다.
   60m 앞 장애물 때문에 즉시 차선을 침범하는 식이었다.
2. **작은 offset 은 아무것도 못 피운다.** 충돌 임계가 `장애물반경 + 1.45m` 라
   경로 중앙 장애물은 1.75m 를 비켜도 못 넘긴다.
3. **좌우 대칭이었다.** 정적장애물 구간과 보행자 구간 모두 자차는 1차로(맨 왼쪽)를
   달리고 왼쪽은 황색 중앙선이다. 왼쪽으로 피하면 중앙선 침범이고 반대편 차로로
   들어가는 것이라 사고 위험이 크다.

실제 회피 미션은 **교차로 한복판을 막은 상자**다. 교차로 안에는 차선이 없으므로
차로 단위로만 움직일 이유가 없다. 필요한 것은 상자를 비켜갈 만큼이다. 그래서
중간 offset 을 두고 비용을 `|offset|` 에 비례시켜 **충돌을 면하는 가장 작은 회피**가
뽑히게 했다. 좌측은 우측이 전부 막혔을 때만 쓰이도록 큰 비용(20)으로 남겼다.

## 8. Frenet(FOT) 확장 훅 — 나중에 시간축 갈아끼우기 쉽게

지금 구조는 사실상 (s, d) 격자의 단순형이다. 아래를 의식해두면 FOT 이식 비용이 최소화된다. (상세: [frenet-ready-design], docs/03-fot_theory.md)

| 현재 | Frenet 확장 방향 |
|------|------------------|
| `LANE_OFFSET`(좌우 벌림) | **횡변위 `d` 후보**로 명시 (Frenet d축) |
| `X_INTERVAL`(x 간격) | **종방향 누적거리 `s` 샘플간격**으로 명시 |
| `weight` 한 배열에 기본+충돌 합산 | **비용 항 분리**(횡offset항 / 충돌항 / …) → 나중 **종방향 항(속도·시간) 삽입** 쉽게 |
| 3차곡선(횡만) | 횡 5차 + 종 4/5차 다항식(시간축)으로 확장 |
| 정적 충돌검사 | 동적장애물 예측 충돌검사 |

## 9. 파라미터 (튜닝 포인트)

| 파라미터 | 값 | 의미 |
|----------|-----|------|
| `LANE_WIDTH` | 3.51 | 차로 폭 [m]. 시뮬 실측(6.2) |
| `LANE_OFFSET` | {0, -1.0, -2.0, -3.0, -3.51, +3.51} | 후보 횡변위(=d) [m]. 6.2 참고 |
| `BASE_WEIGHT` | {0, 1, 2, 3, 4, 20} | 제자리 최우선, 우측 우선, 좌측은 최후수단 |
| `LAT_ACCEL_LIMIT` | 2.94 | 차선변경 중 허용 횡가속도 [m/s^2] = 0.3G |
| `MIN_TRANSITION` | 8.0 | 정지·극저속에서의 전이 길이 하한 [m] |
