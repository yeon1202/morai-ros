# 신호등 behavior 모듈 — 인수인계 브리프

작성일: 2026-07-31
읽는 사람: behavior FSM 중 **신호등 준수**를 맡을 팀원
관련: [30-lattice_design.md](30-lattice_design.md), [40-acc_design.md](40-acc_design.md), [04-runbook.md](04-runbook.md)

이 문서는 **아이디어와 계약**만 다룬다. 실제 코드는 따로 전달한다.

---

## 0. 세 줄 요약

1. planning 은 **"어디로"(`/lattice_path`)** 와 **"얼마나 빨리"(`/target_velocity`)** 만 낸다. 조향은 control 몫이다.
2. 신호등 모듈이 낼 것은 **"지금 허용되는 최대 속도" 딱 하나**다. 나머지는 몰라도 된다.
3. 그 값은 기존 값들과 `min()` 으로 합쳐진다. **서로 간섭하지 않는다.**

---

## 1. 전체 그림

```
[perception]   /Object_topic     장애물·NPC·보행자
[localization] /odom             내 위치·방향
        │
        ▼
   ┌──────────────── planning ────────────────┐
   │  path_manager → local_path               │
   │       ├─→ lattice     (횡: 어디로)       │
   │       └─→ acc_planner (종: 얼마나 빨리)  │
   │              ↑                            │
   │        [신호등 모듈] ← 당신이 만들 것     │
   └──────────────────────────────────────────┘
        │
        ▼
[control]  /lattice_path (따라갈 선)  +  /target_velocity (낼 속도)
```

**횡방향(어디로)과 종방향(얼마나 빨리)이 완전히 분리**되어 있다. 신호등은 **종방향만** 건드린다. 빨간불이라고 경로를 바꿀 일은 없으니까.

---

## 2. `local_path` 가 무엇인가

여기가 이 문서의 핵심이다. 이걸 알아야 나머지가 이해된다.

### 2.1 무엇인가

**지금 내 앞에 놓인 경로 조각**이다.

```
전체 경로 (global path)  ────────────────────────────────────────  2830m, 4544점
                              │←── local_path ──→│
                              현재 위치        약 87m 앞
```

- 토픽: `/local_path` (`nav_msgs/Path`)
- 길이: **140점 ≈ 87m**
- 좌표: **map ENU** — `/odom`, `/Object_topic` 과 같은 좌표계다. 변환 필요 없다
- 발행: `path_tracker` 노드가 매 프레임

### 2.2 왜 전체 경로를 안 쓰고 잘라 쓰나

**"내 앞"이라는 개념이 필요하기 때문이다.**

- lattice: 회피 후보를 그리려면 "지금부터 앞으로" 가 기준이어야 한다
- ACC: "앞차"를 찾으려면 앞뒤 구분이 있어야 한다
- 4544점을 매 프레임 훑는 건 낭비다

`local_path[0]` 이 항상 **차 바로 앞**이라는 게 보장되므로, 소비자는 "몇 번째 점이 몇 m 앞"만 세면 된다.

### 2.3 어떻게 만들어지나

```
① 기록해둔 전체 경로(path_smooth.csv)를 로드
② 지금 내 위치에서 가장 가까운 waypoint 를 찾는다   ← 여기가 까다롭다
③ 그 지점부터 앞으로 140점을 잘라서 발행
```

### 2.4 ②가 까다로운 이유 — 반드시 알아야 할 함정

**"가장 가까운 점을 찾는다"를 전체에서 찾으면 안 된다.**

우리 경로는 **자기 자신과 겹친다**. 특히 **완주 지점과 코스 진입 지점이 물리적으로 0.4m 거리**다. 전체를 훑으면 코스 진입부에서 "완주 지점"을 최근접으로 집는 일이 생긴다. 그러면:

- `local_path` 가 텅 비거나 몇 점만 남는다
- 조향 목표점이 사라져 차가 직진해버린다
- 혹은 인덱스가 거꾸로 가서 **역주행 경로**가 나온다

그래서 **직전 인덱스 주변만 본다**(슬라이딩 윈도우).

```
직전 인덱스 −10 ~ +100 범위에서만 최근접 탐색
그 범위 안에 10m 이내 점이 없으면 → 그때만 전역 재탐색 1회
```

실측으로 옛 방식은 4633지점 중 116곳(2.5%)에서 엉뚱한 인덱스를 집었고, 새 방식은 0건이다.

> **당신에게 왜 중요한가**: 신호등 모듈이 "정지선까지 남은 거리"를 계산할 때 `local_path` 위 인덱스를 쓸 텐데, **그 인덱스가 항상 연속적으로 증가한다는 보장이 이 구조에서 나온다.** 만약 인덱스가 갑자기 튀면 남은 거리가 음수가 되거나 급변한다.

### 2.5 완주 처리

경로 끝에 도달하면 `finished` 플래그가 서고 차가 정지한다. 이게 없으면 완주 지점과 진입 지점이 겹쳐 있어서 **두 바퀴째를 돌기 시작한다**(실제로 겪었다).

## 3. 종방향의 단일 권한 원칙

**속도를 정하는 곳은 오직 한 군데다.**

```
크루즈 55km/h  ┐
곡률 제한      ├→  min()  →  상승률 제한  →  /target_velocity
앞차 추종      │
[신호등]  ←────┘  당신이 여기에 하나 더 얹는다
```

속도 제한 표지판이 여러 개면 **제일 낮은 걸 따르는 것**과 같다. 각자 브레이크를 밟으면 서로 싸우기 때문에, 전부 모아 **최종값 하나**로 낸다.

**이 원칙 덕분에 분담이 쉬워진다.** 당신의 모듈은 다른 항목들이 뭘 하는지 전혀 몰라도 된다.

## 4. 신호등 모듈의 계약

### 출력

> **"지금 허용되는 최대 속도" 하나. 단위는 m/s.**
>
> - 서야 하면 → `0`
> - 상관없으면 → 제한 없음(아주 큰 값)

그게 전부다. `/ctrl_cmd` 를 직접 발행하지 말 것. **두 노드가 같은 토픽에 쓰면 그날로 끝난다.**

### 입력

| 무엇 | 어디서 | 비고 |
|---|---|---|
| 내 위치·속도 | `/odom` (개발 중엔 `/ego_status`) | |
| 앞 경로 | `/local_path` | 정지선까지 거리 계산용 |
| 신호등 상태 | **perception 팀과 협의 필요** | 이 문서 5절 |

## 5. 신호등 상태를 어떻게 받을 것인가

**여기가 당신이 직접 협의해야 할 부분이다.** perception 팀과 인터페이스를 정하고 문서로 남기면 된다. 우리가 이미 그렇게 한 예가 두 개 있다 — [20-perception_interface.md](20-perception_interface.md), [21-localization_interface.md](21-localization_interface.md). 형식을 참고하면 좋다.

최소한 이 셋은 정해야 한다.

1. **토픽 이름과 메시지 타입**
2. **상태 표현** — 적/황/녹 + "안 보임". `morai_msgs` 에 신호등 메시지가 있는지 먼저 확인할 것
3. **어느 신호등인지** — 교차로에는 신호등이 여러 개다. 내 진행방향의 것만 골라야 한다

> **협의 시 반드시 물어볼 것**: 신호등이 **몇 m 앞에서부터 인지되는가**. 이 값이 감속 계획 전체를 좌우한다. 55km/h(15.3m/s)에서 0.3G로 서려면 **40m** 가 필요하다. 30m 앞에서야 보인다면 이미 늦다.

## 6. 정지선 위치를 어떻게 알 것인가

두 가지 방법이 있고, **2번을 권한다.**

### 방법 1 — perception 이 정지선까지 알려준다

깔끔하지만 perception 팀 부담이 커진다. 신호등 인지와 정지선 인지는 다른 문제다.

### 방법 2 — 정지선 위치를 미리 기록해둔다 ★

**코스는 고정이고 신호등은 4곳뿐이다.** 경로 위 어디인지 미리 재두면 된다.

```
① 시뮬에서 차를 각 정지선에 세우고 좌표를 찍는다
② 그 좌표가 전체 경로의 몇 번째 점(또는 시작부터 몇 m)인지 오프라인으로 계산
③ 표로 저장 — 신호등 4개 각각의 "경로상 위치"
④ 주행 중에는 "지금 내 위치 → 다음 정지선까지 남은 거리" 만 빼면 끝
```

**장점이 크다.**

- perception 이 신호등 **색만** 주면 된다. 협의가 단순해진다
- 인지 거리에 안 휘둘린다. 신호등이 안 보여도 정지선이 어디인지는 안다
- 미리 감속을 시작할 수 있다

**우리가 이미 이 방식을 쓰고 있다.** ACC 의 곡률 속도 제한이 그렇다 — 앞으로 커브가 어디 있는지 경로에서 미리 읽어 감속한다. 같은 발상이다.

> 좌표 찍는 방법과 경로상 위치로 환산하는 건 이미 여러 번 해봤다. 필요하면 도와줄 수 있다.

## 7. 감속을 어떻게 계산할 것인가

### 핵심 아이디어

**정지선까지 남은 거리로 "지금 낼 수 있는 최대 속도"가 정해진다.**

```
허용 속도 ≤ √(2 × 감속도 × 남은거리)
```

고등학교 물리다. 지금 이 속도면 남은 거리 안에 설 수 있는가를 뒤집은 것이다.

| 남은 거리 | 0.3G(2.94)로 설 수 있는 최대 속도 |
|---|---|
| 40m | 15.3 m/s (55 km/h) |
| 20m | 10.8 m/s (39 km/h) |
| 10m | 7.7 m/s (28 km/h) |
| 5m | 5.4 m/s (19 km/h) |
| 0m | 0 |

**이 값을 그대로 출력하면 된다.** 멀리 있을 땐 제한이 크니 `min()` 에서 무시되고, 가까워질수록 자연히 낮아져 부드럽게 선다. **별도의 "감속 시작" 판단이 필요 없다.**

> **재사용 가능**: `acc_core.hpp` 의 `curvatureSpeedLimit()` 이 정확히 같은 식을 쓴다(`√(v_curve² + 2·a·d)`). 코드를 참고하면 바로 감이 올 것이다.

### 상태별 처리

| 신호 | 출력 |
|---|---|
| 녹색 | 제한 없음 |
| 적색 | 위 식으로 감속 → 정지선에서 0 |
| 황색 | **딜레마 존 판단 필요.** 아래 참고 |
| 안 보임 | **정책 결정 필요.** 아래 참고 |

### 딜레마 존 — 황색에서 설 것인가 갈 것인가

황색이 됐을 때 **너무 가까우면 서려다 오히려 교차로 한복판에 멈춘다.**

```
설 수 있는 최소 거리 = v² / (2 × 감속도)

남은 거리 > 이 값  →  설 수 있다. 선다
남은 거리 < 이 값  →  못 선다. 그냥 통과한다
```

55km/h에서는 40m다. 즉 **40m 안쪽에서 황색이 되면 통과가 정답**이다.

### "안 보임" 처리 — 반드시 정해야 한다

perception 이 신호등을 놓치는 순간이 반드시 온다(가림, 역광, 규정에 있는 **Foggy 날씨**).

- **직전 상태를 유지할지** vs **보수적으로 정지할지**
- 규정상 신호 위반은 **15초 페널티**, 불필요한 정지는 완주 시간 손해

권하는 방향: **직전 상태를 짧은 시간(예 1~2초) 유지하고, 그보다 오래 끊기면 보수적으로 전환.** 다만 이건 정책이라 팀에서 합의할 것.

## 8. 시뮬 없이 테스트하는 법 ★

**이게 개발 속도를 가장 크게 좌우한다.** perception 의 신호등 인지를 기다릴 필요가 없다.

우리가 이미 이 방식으로 여러 기능을 검증했다.

```
가짜 신호등 publisher 를 만든다
  → 원하는 색을 원하는 타이밍에 쏜다
  → 당신 모듈이 내는 속도를 관찰
  → 시뮬도 주행도 필요 없다. roscore 만 있으면 된다
```

참고할 만한 것들이 이미 있다.

| 도구 | 하는 일 |
|---|---|
| `scripts/test_lattice.py` | 가짜 경로·자차·장애물을 쏘고 lattice 출력을 검증. **9케이스 자동 판정** |
| `src/mock_lead_vehicle.cpp` | 가짜 앞차를 경로 위에 띄워 ACC 검증 |
| `scripts/lap_logger.py` | 한 바퀴 주행을 CSV 로 기록하고 요약 |

`test_lattice.py` 가 실제로 **눈으로는 안 보이던 버그를 찾아냈다.** 충돌 벌점이 후보당 1회가 아니라 waypoint 개수만큼 누적되고 있었는데, 하니스가 아니었으면 못 찾았다.

**당신 모듈도 같은 구조로 만들 것을 강력히 권한다.** 케이스는 이런 것들이다.

- 녹색 → 제한 없음
- 적색 40m 앞 → 감속 시작
- 적색 0m → 0
- 황색 + 가까움 → 통과
- 황색 + 멂 → 정지
- 신호 끊김 → 정책대로

## 9. 미리 알아둘 함정

우리가 실제로 다 당한 것들이다. 시간 낭비를 줄이려면 먼저 읽어둘 것.

| 함정 | 내용 |
|---|---|
| **속도 단위** | `/ego_status` 의 velocity 는 m/s 가 아니라 **km/h** 다. 브릿지가 MORAI 원본을 변환 없이 넘긴다. 우리는 이걸로 세 군데서 당했다. 반대로 우리가 내는 `/target_velocity` 는 **m/s** 다 |
| **위치가 0,0,0** | 규정용 포트(9109)로 받으면 position 이 0 으로 온다. GPS 음영 미션 때문에 의도된 것이다. 개발 중엔 9111 을 쓴다 |
| **MORAI 가 마지막 명령을 문다** | 노드를 그냥 죽이면 차가 마지막 accel 로 계속 간다(실측 5.4 → 17.4 m/s). 반드시 `estop.py` 로 세운다 |
| **로그가 안 찍힌다** | 노드 stdout 은 블록 버퍼링이라 `kill` 하면 통째로 날아간다. **로그가 비었다고 기능이 안 돈 걸로 읽지 말 것.** `stdbuf -oL` 을 붙인다 |
| **로그의 한글이 깨진다** | 컨테이너 로케일 문제. `ROS_INFO` **포맷 문자열에는 한글을 쓰지 말 것**. 주석은 무관 |
| **rosparam 이 남는다** | `_param:=값` 을 한 번 주면 노드를 죽여도 마스터에 남는다. 다음 실행 때 조용히 그 값으로 돈다. `rosparam list` 로 확인 |

전부 [04-runbook.md](04-runbook.md) 7절에 표로 정리돼 있다. 실행·정지 명령어도 거기 있다.

## 10. 정리 — 당신이 할 일

1. **perception 팀과 신호등 인터페이스 협의** → 문서로 남기기 (5절)
2. **정지선 4곳 위치 측정** → 경로상 위치로 환산해 표로 (6절)
3. **가짜 신호등 publisher + 테스트 하니스** 만들기 (8절)
4. **감속 로직 구현** — 출력은 "허용 최대 속도" 하나 (7절)
5. 통합은 마지막에. 그전까진 하니스로만 검증해도 충분하다

**모르는 게 생기면 코드를 뒤지기 전에 물어보는 게 빠르다.** 특히 `local_path` 나 경로 인덱스 관련은 함정이 많아서 혼자 헤매기 쉽다.
