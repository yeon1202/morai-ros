# planning 인수인계 — behavior FSM 합류자용

작성일: 2026-07-31
읽는 사람: behavior FSM 중 **신호등 준수**를 맡을 팀원
관련: [30-lattice_design.md](30-lattice_design.md), [40-acc_design.md](40-acc_design.md), [04-runbook.md](04-runbook.md)

**지금까지 내가 만들어둔 것과, 왜 그렇게 만들었는지**를 적는다.
세부 구현은 코드를 보면 되고, 이 문서는 **구조·근거·세팅** 위주다.

---

## 0. 먼저 알아야 할 두 가지

**① planning 은 조향을 내지 않는다.**
"어디로"(`/lattice_path`)와 "얼마나 빨리"(`/target_velocity`) 둘만 낸다. 핸들·페달로 바꾸는 건 control 몫이다.

**② 횡(어디로)과 종(얼마나 빨리)이 완전히 분리돼 있다.**
lattice 는 횡만, ACC 는 종만 본다. 붙여놓으면 "피할까 설까"를 한 덩어리에서 판단해야 해서 경우의 수가 폭발한다. 나눠두면 각자 한 가지만 고민하면 되고, **behavior 가 붙을 때도 종방향 쪽에만 얹으면 된다.**

```
[perception] /Object_topic ─┐
[localization] /odom ───────┤
                            ▼
   path_tracker ──/local_path──┬──→ lattice_planner ──→ /lattice_path
                               └──→ acc_planner ─────→ /target_velocity
                                          ▲
                                    [신호등] ← 여기 붙는다
```

## 1. global path — 경로를 어떻게 만들었나

모든 것의 토대다. lattice 도 ACC 도 이 위에서 돈다.

### 구성

```
approach.csv   980점   656m   스폰 지점 → 대회 라인 진입
course.csv    3571점  2178m   대회 라인 한 바퀴
      ↓ path_join.py
path.csv      4544점  2830m   이음매 = idx 972
      ↓ path_smoother.py (이동평균)
path_smooth.csv               ← 실제로 쓰는 파일
```

**대회 구간은 idx 972 부터**다. 그 앞은 차를 라인에 올리기 위한 접근구간이라 대회 코스가 아니다.

### 왜 두 개로 나눴나

시뮬 스폰 지점이 코스에서 **58~61m 떨어진 다른 도로**다. 그냥 코스만 기록하면 출발하자마자 경로에서 벗어난 상태가 되고, pure_pursuit 은 "차가 경로 위에 있다"를 전제하는 알고리즘이라 목표점이 옆 90도에 잡혀 **최대 조향으로 폭주**한다. 2m만 벗어나도 이미 포화다.

그래서 스폰 → 진입까지를 따로 기록해 앞에 붙였다.

### 기록할 때 신경 쓴 것

- **이음매 정밀도**: approach 끝이 course 시작에 **0.15m** 까지 붙는다. 처음엔 5.84m 였는데 그대로 이으면 이음매에서 횡으로 5.8m 점프해 추종이 깨진다(차로 폭보다 크다). 접근구간을 다시 기록해 맞췄다
- **course 는 출발점을 조금 지나서 끊는다**. 겹친 만큼은 `path_join.py` 가 잘라낸다. 반대로 못 미치면 경로가 끊긴다
- **차로 중앙을 매끄럽게** 몰았다. 여기서 생긴 오차는 추종으로 절대 복구되지 않는다

재기록 절차는 [04-runbook.md](04-runbook.md) 6절에 다 적어뒀다.

## 2. local path — 어떻게 만드나

### 무엇인가

**지금 내 앞에 놓인 경로 조각**이다.

- 토픽 `/local_path` (`nav_msgs/Path`), **140점 ≈ 87m**
- 좌표계 **map ENU** — `/odom`, `/Object_topic` 과 같다. 변환 불필요
- `path_tracker` 노드가 매 프레임 발행

### 왜 잘라 쓰나

**"내 앞"이라는 개념이 필요해서**다.

- lattice: 회피 후보를 그리려면 "지금부터 앞으로"가 기준이어야 한다
- ACC: "앞차"를 찾으려면 앞뒤 구분이 있어야 한다
- 4544점을 매 프레임 훑는 건 낭비다

`local_path[0]` 이 항상 **차 바로 앞**이라 소비자는 "몇 번째 점이 몇 m 앞"만 세면 된다.

### 길이를 140점(87m)으로 잡은 이유

ACC 가 이 경로 위에서 앞차를 찾으므로 **ACC 의 지평선이 곧 이 길이**다. 60km/h 기준으로 계산했다.

```
평형 간격 = 16.67×1.0 + 5 + 4.635 = 26.3m
제동 거리 = v²/2a = 46m
반응 여유 = 4초 × 16.67 = 67m
→ 87m
```

### ⚠️ 최근접 waypoint 탐색 — 여기가 제일 중요하다

**"가장 가까운 점"을 전체에서 찾으면 안 된다.**

우리 경로는 **자기 자신과 겹친다**. 특히 **완주 지점과 코스 진입 지점이 물리적으로 0.4m 거리**다. 전체를 훑으면 진입부에서 "완주 지점"을 집는 일이 생기고, 그러면

- `local_path` 가 텅 비어 조향 목표점이 사라진다(차가 직진해버림)
- 인덱스가 거꾸로 가서 **역주행 경로**가 나온다

그래서 **직전 인덱스 주변만 본다.**

```
SEARCH_BACK    = 10      직전 인덱스에서 뒤로 (정지·후진·노이즈 대비)
SEARCH_AHEAD   = 100     앞으로
RESET_DISTANCE = 10.0m   창 안에 이보다 가까운 점이 없으면 그때만 전역 재탐색 1회
```

회귀 테스트(`scripts/test_path_manager.py`)로 고정해뒀다. 옛 방식은 4633지점 중 **116곳(2.5%)** 에서 엉뚱한 인덱스를 집었고, 새 방식은 **0건**이다.

> **당신에게 왜 중요한가**: 정지선까지 남은 거리를 계산할 때 경로 인덱스를 쓸 텐데, **그 인덱스가 항상 연속적으로 증가한다는 보장이 이 구조에서 나온다.** 이게 없으면 남은 거리가 갑자기 튀거나 음수가 된다.

### 완주 처리

경로 끝 3점 이내에 닿으면 `finished` 가 서고 그 뒤로는 탐색을 멈춘 채 정지한다. 이게 없으면 완주 지점과 진입 지점이 겹쳐 있어서 **0.7초 만에 두 바퀴째를 돌기 시작한다**(실제로 겪었다).

## 3. lattice — 횡방향을 어떻게 구성했나

### 흐름

```
① 장애물 수집        원(중심 + 반경)으로. 반경 = 0.5×max(size.x, size.y), 최소 0.3m
② 회피 트리거 판정   경로 위에 장애물이 있나? 없으면 local_path 그대로 통과
③ 후보 경로 생성     좌우 offset 마다 3차곡선으로 부드럽게 빠졌다 복귀
④ 충돌 검사 + 선택   각 후보에 비용 → 최소비용 argmin
⑤ 발행              /lattice_path (선택) + /lattice_candidates (RViz 시각화)
```

### 설정과 근거

```
LANE_WIDTH  = 3.51m           차로 폭. 시뮬 실측
LANE_OFFSET = {0, -1.0, -2.0, -3.0, -3.51, +3.51}     음수가 우측
BASE_WEIGHT = {0,  1.0,  2.0,  3.0,   4.0,   20.0}
```

**차로 폭 3.51m 는 실측값이다.** 직선구간(곡률반경 39928m)에서 차선 두 줄의 좌표를 찍어 도로 수직 성분을 계산했다. baseline 을 어떻게 잡아도 3.510m 로 일정했다(편차 0.001m). 한국 고속도로 표준 3.5m 와도 맞는다.

**후보를 이렇게 잡은 이유 셋.**

1. **`0` 후보가 있어야 한다.** 예전엔 없어서, 회피 트리거가 걸리기만 하면 무조건 1m 이상 움직였다. 60m 앞 장애물 때문에 즉시 차선을 침범하는 식이었다
2. **작은 offset 은 아무것도 못 피운다.** 충돌 임계가 `장애물반경 + 1.45m` 라 경로 중앙 장애물은 1.75m 를 비켜도 못 넘긴다. 그런데 예전 비용표는 그 쓸모없는 후보들이 제일 쌌다
3. **좌우가 대칭이면 안 된다.** 정적장애물 구간과 보행자 구간 모두 **자차는 1차로(맨 왼쪽)** 를 달리고 **왼쪽은 황색 중앙선**이다. 왼쪽으로 피하면 중앙선 침범이고 반대 차로로 들어가는 것이라 위험하다. 그래서 **회피는 우측**, 좌측은 우측이 전부 막혔을 때만 쓰이도록 큰 비용(20)으로 남겼다

비용을 `|offset|` 에 비례시켜 **충돌을 면하는 가장 작은 회피**가 뽑히게 했다. 실제 미션이 **교차로 한복판의 상자**인데 교차로엔 차선이 없으니 차로 단위로만 움직일 이유가 없다.

### 전이 길이 — 거리가 아니라 시간

옆으로 옮기는 데 앞으로 쓰는 거리를 **속도 비례**로 잡는다.

```
xf = v × 2.68초       (LAT_ACCEL_LIMIT 2.94 = 0.3G 에서 유도)
20km/h → 14.9m,  55km/h → 40.9m,  둘 다 횡가속도 0.30G
```

**레퍼런스 코드는 waypoint 개수로 정하고 있었고 하한이 있어서, 주행의 절반이 약 24m 로 고정돼 있었다.** 거리를 고정하면 시간이 속도에 따라 널뛰고, 횡가속도가 0.12G ~ 0.72G 로 변한다. 저속에선 너무 느긋해 15m 앞 상자를 못 피우고, 고속에선 우리 한계의 2.4배를 요구해 차가 못 따라간다. 자세한 유도는 [30-lattice_design.md](30-lattice_design.md) 6.1.

### 보행자는 lattice 가 손 뗐다 ★

**보행자는 회피 트리거에서 제외했다.** 미션이 횡단보도로 신호를 위반하며 뛰어드는 사람이라, 옆으로 꺾으면 사람이 뛰어든 쪽이나 반대 차로로 들어갈 수 있다. **보행자는 피하는 대상이 아니라 서는 대상**이다.

다만 다른 이유로 이미 회피 중일 때 보행자를 뚫고 가면 안 되므로 **후보 충돌 검사에는 포함**한다.

> **즉 보행자 급정지는 온전히 behavior 몫이다.** 여기서 안 잡으면 아무도 안 잡는다.

### 회피 불가 상황

모든 후보가 막히면 경고를 띄우고 최소비용 후보를 낸다. **정지는 lattice 가 하지 않는다.**

```
[lattice] all candidates blocked - behavior/ACC must stop
```

**지금 이 경고를 아무도 듣고 있지 않다.** behavior 가 이걸 신호로 받아 감속·정지해야 한다.

## 4. ACC — 종방향을 어떻게 구성했나

### 설계 원칙 하나

> **`/target_velocity` 가 종방향의 유일한 권한이다.**

속도를 정하는 이유가 여럿이다. 각자 브레이크를 밟게 하면 서로 싸운다. 그래서 전부 한 곳에서 계산해 **최종값 하나**로 낸다.

```
크루즈 55km/h  ┐
곡률 제한      ├→  min()  →  상승률 제한  →  /target_velocity (m/s)
앞차 추종      │
[신호등]  ←────┘  당신이 여기에 하나 더 얹는다
```

속도 제한 표지판이 여러 개면 제일 낮은 걸 따르는 것과 같다. **새 이유가 생기면 `min()` 에 항목 하나 추가하면 끝이다.**

### 세 가지 제한

**① 앞차 추종**

```
안전거리 = 내 속도 × 1.0초 + 5.0m + 차 길이 4.635m
```

**앞차 선택은 경로를 따라간 거리(s)로 한다.** 처음엔 직선거리로 했는데 커브에서 틀린다 — 반경 20m 사분원이면 실제 거리 31.4m 인데 직선거리는 28.3m 로 나와 3m 를 과소평가하고, 앞차인지 뒤차인지 구분도 안 된다. 지금은 객체를 경로에 수직 투영해 `(s, d)` 를 구한다. `d` 로 "내 차선인가", `s` 차이의 부호로 "앞인가 뒤인가"를 본다.

**② 곡률 제한 — 커브 전에 미리 감속**

```
반경 R 을 횡가속 한계로 도는 속도 = √(a_lat × R)
그 커브가 d 앞이면        허용 속도 ≤ √(v_curve² + 2 × a_brake × d)
→ 전방 모든 지점의 최솟값을 쓴다
```

실제 프로필은 최저 15 / 평균 53 / 최고 60 km/h 다.

> **신호등 감속도 이 식과 같은 꼴이 될 것이다.** `√(2×a×d)` 로 남은 거리에서 허용 속도를 뽑으면, 멀 땐 제한이 커서 `min()` 에서 무시되고 가까워질수록 자연히 낮아진다. **"이제 감속 시작" 같은 판단이 따로 필요 없다.** 코드는 `acc_core.hpp` 의 `curvatureSpeedLimit()` 을 보면 된다

**③ 상승률 제한 — 커브를 빠져나올 때**

곡률 제한은 앞쪽만 보므로 커브 정점을 지나는 순간 제한이 즉시 풀린다. 목표속도가 한 스텝에 4 → 15 m/s 로 점프하고, 차는 아직 복귀 중이라 **S자로 사행**했다. 그래서 목표속도를 **초당 1.0 m/s² 씩만** 올린다. 탈출 후 CTE 진동 폭이 1.22m → **0.21m** 로 줄었다.

**감속은 절대 제한하지 않는다.** 급정지가 늦어지면 사람이 다친다.

### 주요 설정값

```
time_gap 1.0s        default_space 5.0m      vehicle_length 4.635m
distance_threshold 2.5m (내 차선 판정)        lookahead 60m
lat_accel_limit 2.94 (0.3G)                  brake_accel 2.0
curve_baseline 10.0m                         curve_min_speed 2.0
accel_rate_limit 1.0                         rate_limit_windup 2.0
cruise 55 km/h  (규정 상한은 60)              max 60 km/h (하드캡)
```

**크루즈가 55인 이유**: target 60 으로 달렸을 때 실측이 60.1~60.2 로 넘어갔다. 규정상 60 초과는 15초 + 3초당 15초 페널티라 오버슈트 여유를 뒀다.

`curve_baseline` 이 10m 인 이유: 기록 경로에는 지터가 있어서 3m 로 재면 실제로는 없는 급커브가 잡힌다(R=4.2m 가 나왔는데 차량 최소회전반경보다 작아 물리적으로 불가능한 값이었다).

## 5. 당신이 붙일 자리

**ACC 와 같은 층**이다. lattice 와는 상관없다 — 빨간불이라고 경로를 바꾸진 않으니까.

### 계약

> **출력은 "지금 허용되는 최대 속도" 하나. 단위 m/s.**
> 서야 하면 0, 상관없으면 제한 없음(큰 값).

그게 전부다. **`/ctrl_cmd` 를 직접 발행하지 말 것.** 두 노드가 같은 토픽에 쓰면 그날로 끝난다.

### 입력으로 쓸 수 있는 것

| 무엇 | 토픽 | 비고 |
|---|---|---|
| 내 위치·속도 | `/odom` (개발 중엔 `/ego_status`) | ⚠️ velocity 단위 주의. 9절 |
| 앞 경로 | `/local_path` | 정지선까지 거리 계산용 |
| 신호등 | 시뮬에서 발행 중 | 어느 신호등이 내 진행방향인지 고르는 건 확인 필요 |

### 정지선 위치는 미리 재두는 걸 권한다

코스는 고정이고 신호등은 **4곳**뿐이다. 시뮬에서 차를 각 정지선에 세워 좌표를 찍고, 그게 경로상 몇 m 지점인지 오프라인으로 환산해 표로 저장해두면

- 주행 중에는 "지금 위치 → 다음 정지선까지 남은 거리" 만 빼면 된다
- 신호등이 안 보여도 정지선 위치는 안다
- 미리 감속을 시작할 수 있다

**곡률 제한이 정확히 이 방식이다.** 앞으로 커브가 어디 있는지 경로에서 미리 읽어 감속한다. 좌표를 경로상 위치로 환산하는 건 여러 번 해봤으니 필요하면 도와주겠다.

## 6. 세팅 — 지금 환경이 어떻게 돼 있나

### 컨테이너

```
morai-sim   MORAI 시뮬레이터
morai-dev   ROS1 noetic 개발환경
둘 다 --network host 라 127.0.0.1 로 통신한다
catkin_ws 는 호스트 마운트 → 호스트에서 파일 고치면 컨테이너에 바로 반영
Python 노드는 재빌드 불필요, C++ 만 catkin_make
```

### 브릿지 (UDP ↔ ROS)

팀 공용 `udp_bridge.py` 를 쓴다. **여기 하나 알아둘 것이 있다.**

```
9109  Competition Vehicle Status  ← 규정상 이것만 허용. 그런데 position 이 0,0,0
9111  Ego Vehicle Status          ← ground truth 위치가 나온다. 개발 중엔 이걸 쓴다
```

규정 포트는 **위치를 안 준다.** GPS 음영 미션이 있어서 의도적으로 뺀 것이다. 최종본은 localization 팀의 `/odom` 을 구독해야 한다. 개발 중엔 `/ego_status` 를 쓰고, 나중에 한 줄로 교체할 수 있게 설계해뒀다.

### 실행 · 정지

전부 [04-runbook.md](04-runbook.md) 에 있다. **정지 절만은 꼭 읽어라.**

```
정상 정지 : rosnode kill /path_tracker && rosrun path_tracking estop.py
비상 정지 : rosrun path_tracking estop.py
```

**MORAI 는 마지막으로 받은 `/ctrl_cmd` 를 계속 물고 있는다.** 노드만 죽이면 차가 마지막 accel 명령으로 계속 가속한다(실측 5.4 → 17.4 m/s). `pkill` 은 roslaunch 노드에 안 듣는다.

### 파라미터가 어디 있나

| 무엇 | 어디 |
|---|---|
| ACC 파라미터 | `acc_core.hpp` 의 `AccParams` 기본값, `acc.launch` 에서 덮어씀 |
| lattice 파라미터 | `lattice_planner.cpp` 상수 (아직 ROS param 아님) |
| 추종 파라미터 | `path_tracker.py` 상단 상수 |

ACC 는 `pnh.param` 으로 노출돼 있어 **재빌드 없이** 바꿀 수 있다.

```
roslaunch path_tracking acc.launch cruise_speed_kmh:=30
```

- **lattice, ACC, 경로 전반**

## 9. 미리 알아둘 함정

전부 내가 실제로 당한 것들이다. 같은 데서 시간 버리지 말라고 적는다.

| 함정 | 내용 |
|---|---|
| **속도 단위** | `/ego_status` 의 velocity 는 m/s 가 아니라 **km/h** 다. 브릿지가 MORAI 원본을 변환 없이 넘긴다. 세 군데서 당했다(한 곳은 이미 km/h 인 걸 또 ×3.6 해서 12.96배가 됐다). 반대로 우리가 내는 `/target_velocity` 는 **m/s** 다 |
| **위치가 0,0,0** | 규정 포트(9109)는 position 을 안 준다. 개발 중엔 9111 |
| **MORAI 가 마지막 명령을 문다** | 노드를 그냥 죽이면 차가 계속 간다. `estop.py` 로 세운다 |
| **로그가 안 찍힌다** | 노드 stdout 은 블록 버퍼링이라 `kill` 하면 통째로 날아간다. **로그가 비었다고 기능이 안 돈 걸로 읽지 말 것.** `stdbuf -oL` 을 붙이거나 토픽을 직접 관측한다 |
| **로그의 한글이 깨진다** | 컨테이너 로케일 문제. `ROS_INFO` **포맷 문자열에는 한글을 쓰지 말 것.** 주석은 무관 |
| **rosparam 이 남는다** | `_param:=값` 을 한 번 주면 노드를 죽여도 마스터에 남는다. 다음 실행 때 조용히 그 값으로 돈다. `rosparam list` 로 확인 |
| **노드 중복 실행** | 같은 이름 노드를 두 번 띄우면 ROS 가 먼저 뜬 쪽을 죽인다. `/local_path` 가 끊기면 ACC 가 앞차를 못 찾는다 |
| **절전 후 GPU** | 노트북을 절전했다 오면 컨테이너가 GPU 를 잃는다. `docker compose down && up -d` |
