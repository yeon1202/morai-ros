## 3. 메시지 구조 (제안)

기존 `RecognizedObject` / `RecognizedObjectArray` 명명 규칙에 맞췄다.

### `LaneLine.msg` — 검출된 경계선 하나

```
# 어느 쪽 선인가
uint8 SIDE_UNKNOWN = 0
uint8 SIDE_LEFT    = 1
uint8 SIDE_RIGHT   = 2
uint8 side

# 선의 종류 (planning 이 "넘어도 되는가" 를 판단하는 데 쓴다)
uint8 TYPE_UNKNOWN      = 0
uint8 TYPE_SOLID        = 1   # 실선
uint8 TYPE_DASHED       = 2   # 점선 (차선변경 가능)
uint8 TYPE_DOUBLE_SOLID = 3   # 중앙선/이중실선 (침범 시 벌점)
uint8 type

uint8 COLOR_UNKNOWN = 0
uint8 COLOR_WHITE   = 1
uint8 COLOR_YELLOW  = 2
uint8 COLOR_BLUE    = 3
uint8 color

# 차량 좌표계에서의 선 모양:  y = c0 + c1*x + c2*x^2 + c3*x^3   [m]
#   x = 전방, y = 좌측 (아래 4-(a) 참고)
#   2차까지만 맞췄으면 c3 = 0 으로 채운다
float32[4] coeff

float32 x_min        # 이 다항식이 유효한 전방 구간 시작 [m]
float32 x_max        # 끝 [m]
float32 confidence   # 0.0 ~ 1.0
```

### `LaneLineArray.msg` — 한 프레임

```
Header header        # stamp = 이미지 촬영 시각, frame_id = "base_link"
LaneLine[] lines     # 못 봤으면 빈 배열
```

## 4. 준수 요건 (통합 실패 1순위)

### (a) 좌표계 — ROS 표준(REP 103)을 그대로 따른다

```
x = 차량 전방,  y = 차량 좌측,  z = 위
```

**부호를 따로 약속하지 않는다.** 표준을 따르면 자동으로 정해진다.

- 차가 차선 한가운데 있으면 왼쪽 선은 `c0 ≈ +1.755`, 오른쪽 선은 `c0 ≈ −1.755`
  (차로폭 실측 3.51 m 기준)
- 차가 오른쪽으로 치우치면 **양쪽 `c0` 가 모두 커진다**(선들이 왼쪽으로 보인다)

> **왜 스칼라 하나로 안 받는가**: "차선 중심에서 0.3 m" 같은 값을 주고받으면
> **왼쪽이 +인지 오른쪽이 +인지를 문서로 약속**해야 한다. 이게 뒤집히면 보정이
> 오차를 두 배로 키우는 방향으로 작동하고, 증상이 "차가 차선 밖으로 밀려남" 이라
> 실주행에서 위험하다. **선 자체를 표준 좌표계로 주면 이 위험이 원천적으로 없다.**

### (b) 단위

- `coeff`, `x_min`, `x_max` = **m**
- `confidence` = 0.0 ~ 1.0 (무차원)
- 각도는 안 쓴다 (필요하면 planning 이 `atan(c1)` 로 구한다)

### (c) 빈 경우 처리

**차선을 못 봐도 빈 배열로 계속 발행한다.** (`20-perception_interface.md` 3-(c) 와 같은 규약)

교차로 한가운데, 가림, 노면 마모 등으로 못 보는 구간이 반드시 생긴다. 그때
**발행을 멈추면 planning 은 "노드가 죽었나 안 보이나" 를 구분할 수 없다.**
빈 배열이 오면 planning 은 그 프레임을 그냥 건너뛴다.

### (d) ⚠️ 타임스탬프는 "촬영 시각" 이어야 한다 — 이 명세에서 제일 중요하다

`header.stamp` 에 **발행 시각(`ros::Time::now()`)을 찍지 말고, 입력 이미지의
`header.stamp` 를 그대로 복사**해 주세요.

**왜 중요한가.** 차가 회전 중이면 **지연이 그대로 각도 오차가 된다.**

```
heading 오차 = 요레이트 × 지연시간
```

우리 급커브 기준 요레이트가 0.25 rad/s 다. 여기에 지연을 곱하면,

| 지연 | 급커브에서 생기는 오차 |
|---|---|
| 0.10 초 | 1.4° |
| 0.20 초 | 2.9° |
| 0.30 초 | 4.3° |

현재 `/odom` 의 yaw 오차가 **중앙 0.17°** 다. 즉 **지연을 모르면 차선 정보가
지금 있는 것보다 나쁠 수 있다.** 스탬프가 정확하면 planning 이 보정할 수 있다.

⚠️ **알려진 한계 (planning 쪽 문제)**: 지금 `udp_bridge` 가 카메라 이미지에
**도착 시각**을 찍는다(`rospy.Time.now()`). MORAI 가 이미지를 만들어 UDP 로
보내는 데 걸리는 시간이 여기 안 들어가 있다. GPS 에서 같은 문제를 실측해
**0.30초**를 확인하고 스탬프를 되감아 보정했는데, 카메라는 아직 안 쟀다.
→ **planning 이 잰다.** 그전까지 이미지 스탬프는 "이보다 이르지는 않다" 는
하한으로만 쓴다. **perception 쪽에서는 이미지 스탬프를 그대로 복사만** 하면 된다.

### (e) 다항식의 유효 구간을 정확히 채워 주세요

`x_min` / `x_max` 는 **실제로 차선을 본 구간**이어야 한다. 그 밖으로 외삽하면
값이 급격히 틀어지므로 planning 은 구간 밖을 쓰지 않는다.

⚠️ **planning 이 제일 쓰고 싶은 값은 `x = 0`(차 바로 옆)에서의 `c0` 다.**
그런데 보닛에 가려 보통 `x_min` 이 3~5 m 근처에서 시작한다. 그러면 `x = 0` 은
외삽이 된다. **`x_min` 이 실제로 얼마인지 알려주시면** planning 이 그만큼을
감안해서 쓴다. (6장 협의사항 ③)

## 5. Planning 이 이걸로 무엇을 하는가

**왜 이 형태로 달라고 하는지**를 알면 값을 채울 때 판단하기 쉬우실 것 같아 적는다.

### (a) 차선 중심 대비 횡오차 — 주 용도

우리 전역경로가 **MGeo 차선 중심선 위에 정확히**(거리 0.000 m) 놓여 있음을 실측으로
확인해 뒀다. 그래서 "차선 중심에서 얼마나 벗어났나" 를 `/odom` 과 카메라 **두 경로로
독립적으로** 얻을 수 있고, 둘을 비교하면 위치 추정이 얼마나 틀렸는지 알 수 있다.

```
양쪽 다 보임 :  y_c = (c0_left + c0_right) / 2
왼쪽만 보임  :  y_c = c0_left  − 1.755
오른쪽만 보임:  y_c = c0_right + 1.755

차가 차선 중심에서 벗어난 양  d = −y_c        (d > 0 이면 차가 중심의 왼쪽)
```

**한쪽만 보여도 쓸 수 있다는 게 선을 따로 받는 이유 중 하나다.**

### (b) 실선/점선 — 이건 차선 인지만이 줄 수 있다

지금 planning 의 회피 알고리즘은 옆 차선으로 나가는 후보(`±3.51 m`)를 만드는데,
**그 선을 넘어도 되는지를 모르는 채로** 고르고 있다. 중앙선 침범은 벌점이므로
`TYPE_DOUBLE_SOLID` / `TYPE_SOLID` 는 회피 후보를 거르는 데 직접 쓰인다.

**장애물 회피보다 이쪽이 점수에 더 직접적일 수 있다.**

### (c) heading (`c1`) — 받긴 하지만 당장은 안 쓴다

`/odom` 의 yaw 가 이미 중앙 0.17° 로 정확하고, 4-(d) 의 지연 문제 때문에 커브에서
오히려 나빠질 수 있다. **같은 다항식에서 공짜로 나오는 값이라 받아두는 것**이고,
지연을 실측한 뒤에 쓸지 정한다. **따로 계산해서 넣으실 필요는 없다.**

### (d) 안 쓰는 것

`z`, 도로 경계(연석), 정지선은 이번 범위가 아니다. 정지선은 planning 이 좌표를
직접 들고 있다(`52-stopline_table.txt`).

## 6. 협의 필요 사항

| # | 항목 | 왜 묻는가 |
|---|---|---|
| ① | **토픽 이름과 메시지 패키지** | `/lane_lines`, `autonomous_driving/LaneLineArray` 로 괜찮은지. 이미 다른 이름으로 만드셨으면 그쪽에 맞추겠다 |
| ② | **다항식으로 내보낼 수 있는지** | 내부적으로 점 목록만 있다면 점 배열로 받아도 된다. 그 경우 형식을 알려주시면 메시지를 그렇게 고친다 |
| ③ | **`x_min` 이 실제로 얼마인지** | 4-(e) 참고. `x = 0` 까지 유효한지, 아니면 몇 m 부터인지 |
| ④ | **실선/점선 구분이 되는지** | 5-(b) 참고. 안 되면 `TYPE_UNKNOWN` 으로 채우고, planning 은 그 기능을 뺀다 |
| ⑤ | **이미지 스탬프를 복사할 수 있는지** | 4-(d) 참고 |
| ⑥ | **몇 번 차선인지 아는지** (선택) | "1차선인가 2차선인가" 를 아신다면 유용하다. 지도 매칭이 필요한 일이라 **안 되면 빼도 된다** |
| ⑦ | **`lane_detection_node` 를 어느 브랜치에 올릴지** | 1장 참고 |

## 7. 통합 단계

`20-perception_interface.md` 5장과 같은 방식으로, **한 번에 다 붙이지 않는다.**

### 단계 1 — 토픽만 흘려보내기

perception 이 발행만 하고, planning 은 **기록만** 한다. 조향은 한 톨도 안 바뀐다.

**여기서 세 가지를 확인한다.**

- 카메라가 본 횡오차가 `/odom` 이 말하는 값과 **한쪽으로 치우쳐 있지 않은가**
  (치우침이 있으면 그건 영구적인 주행 치우침이 된다. 차로 여유가 좌우 각 0.81 m 뿐이라
  0.2 m 치우침이면 4분의 1을 먹는다)
- 카메라 값이 `/odom` 보다 **덜 떨리는가** (`/odom` 은 95% 기준 4 cm 로 떤다)
- GPS 음영구간에서 둘의 차이가 **커지는가** (커지면 위치 이상 탐지에 쓸 수 있다)

```
rostopic hz   /lane_lines     # 15Hz 근처
rostopic echo /lane_lines     # c0 부호가 실제 치우친 방향과 맞는지 눈으로 확인
```

**부호 확인은 반드시 이 단계에서 한다.** 차를 일부러 왼쪽으로 붙여놓고
`c0` 가 어떻게 변하는지 같이 보면 몇 분이면 끝난다.

### 단계 2 — 실선/점선을 회피 판단에 반영

`TYPE_*` 만 먼저 쓴다. 횡오차 보정은 아직 안 켠다.

### 단계 3 — 횡오차 보정

단계 1에서 치우침이 없고 `/odom` 보다 매끄럽다고 확인된 경우에만 켠다.
**planning 안에서만 쓰고 localization(EKF)에는 넣지 않는다** — 이유는 planning 쪽
설계 문서에 정리해 두었다.
