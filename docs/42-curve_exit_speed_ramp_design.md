# 커브 탈출 속도 상승률 제한 설계

작성일: 2026-07-29
대상: `acc_core.hpp`, `acc_planner.cpp`
관련: `40-acc_design.md`(ACC 전반), `30-lattice_design.md`

## 1. 문제

접근구간 유턴(idx 150~170, 최소 R=6.03m)을 통과한 직후 차량이 S자로 사행한다.

실측 로그(2026-07-29, `MAX_STEER` 0.65 적용 후):

```
idx 174  CTE 2.06m  v=6.4 m/s   steer +0.712 rad
idx 181  CTE 1.67m  v=8.1 m/s   steer +0.036
idx 190  CTE 0.55m  v=8.9 m/s   steer -0.565     경로를 지나쳐 반대로 꺾음
idx 198  CTE 1.64m  v=8.6 m/s   steer -0.613     다시 반대편으로 벌어짐
idx 205  CTE 1.77m  v=10.3 m/s
idx 212  CTE 0.63m  v=12.3 m/s
```

CTE 가 2.06 → 1.67 → 0.55 → 1.64 → 1.77 → 0.63 으로 진동하는 동안 속도가
6.4 → 12.3 m/s 로 계속 오른다. 복귀 조향이 채 수렴하기 전에 속도가 붙어
오버슛이 커진다.

### 원인

`curvatureSpeedLimit()` 은 `/local_path`(차량 앞쪽 waypoint) 만 훑는다.

```cpp
for (size_t i = 0; i < path.size(); ++i) {
    double d = cum[i];                                   // 경로 시작(=ego)부터의 거리
    double v_now = sqrt(v_curve*v_curve + 2*brake_accel*d);
    if (v_now < limit) limit = v_now;
}
```

커브 정점을 지나는 순간 그 곡률 점들이 `local_path` 에서 빠져나가고 제한이
같은 프레임에 즉시 풀린다. 커브 **진입**에는 감속 프로파일(`+2*a*d`)이 있지만
커브 **탈출**에는 대응하는 가속 프로파일이 없어서 목표속도가 한 스텝에
크루즈(55km/h)까지 열린다.

### 문제의 범위

사행의 1차 원인은 커브 정점에서의 조향 포화다. 유턴 정점에서 pure_pursuit
요구 조향이 0.817 rad(46.8도)까지 올라가 `MAX_STEER`(0.65)에 잘리고, 그 결과
차량이 CTE 2.06m 로 벌어진 채 커브를 빠져나온다. 속도 상승은 그 뒤 복귀 과정을
증폭하는 2차 요인이다.

이 문서는 2차 요인만 다룬다. 벌어짐 자체(2.06m)는 별도 과제로 남는다.

## 2. 설계

### 2.1 판정 방식 선택

"아직 커브 안"을 판정하는 방법으로 세 가지를 검토했다.

| 방식 | 내용 | 판단 |
|---|---|---|
| 경로 기준 | 지나온 경로 N m 를 `local_path` 에 포함해 곡률 검사 | `/local_path` 인터페이스가 바뀌어 lattice·ACC 앞차판정(`s_ego` 기준)까지 영향. 범위 과대 |
| 차량 기준 | `/ego_status.front_steer_angle` 이 크면 커브로 간주 | 물리적으로 직관적이나 새 입력 의존이 생김 |
| **이력 기준** | **직전 목표속도에서 정해진 상승률로만 올림** | **채택.** 별도 종료 판정이 불필요하다 - 천천히 오르는 것 자체가 보수적 종료 판정이 된다. 상태 변수 2개, 인터페이스 변경 없음 |

### 2.2 상승률 값

유턴 탈출에서 실측된 **실제** 가속도는 4.7 → 8.1 m/s (1.43초) = 약 2.4 m/s^2 다.
목표속도는 그 순간 15.3 m/s 로 한 번에 뛰었으나 차량이 그 이상 따라가지 못했다.
따라서 2.4 이상으로 제한하면 효과가 없다.

4.2 m/s(15km/h) → 15.3 m/s(55km/h) 도달 시간:

| 상승률 | 도달 시간 | 현재 대비 |
|---|---|---|
| 2.0 m/s^2 | 5.6초 | +1.0초 |
| **1.0 m/s^2** | **11.1초** | **+6.5초** |
| 0.5 m/s^2 | 22.2초 | +17.6초 |

경로의 48%가 60km/h 미만이라 커브 탈출이 반복된다. 완주 192초 기준으로 0.5는
비용이 크다. **1.0 m/s^2 로 시작하고 파라미터로 조정한다.**

### 2.3 순수 함수 (`acc_core.hpp`)

```cpp
// 목표속도의 "상승"만 제한한다. 감속은 그대로 통과시킨다.
inline double rampTarget(double prev, double desired, double ego_vel,
                         double dt, const AccParams& p);
```

동작 순서:

1. `dt <= 0` — `desired` 를 그대로 반환한다. 제한 로직이 차량을 잠그는 상황을
   만들지 않는다.
2. `dt` 를 `[0, rate_dt_max]` 로 자른다. 프레임이 끊겨 `dt` 가 커진 경우 그만큼
   목표가 한 번에 뛰는 것을 막는다.
3. 윈드업 억제 — `prev = min(prev, ego_vel + rate_limit_windup)`
4. `desired <= prev` — `desired` 를 그대로 반환한다. 감속은 절대 늦추지 않는다.
   급정지나 앞차 제동에 대한 반응이 느려지면 안전 문제가 된다.
5. `desired > prev` — `min(desired, prev + accel_rate_limit * dt)`

**안전 불변식: 반환값은 어떤 경로로도 `desired` 를 넘지 않는다.** 이 함수는 목표를
늦출 뿐 높이지 않는다. 크루즈 상한(60km/h 규정)과 곡률 제한은 이미 `desired` 에
반영되어 있으므로, 이 불변식이 지켜지는 한 제한을 우회할 수 없다.

3번(윈드업)이 4번(감속 통과)보다 먼저 오는 순서에 주의한다. `prev` 가 실제 속도보다
크게 앞서 있으면 `desired` 가 직전보다 낮아진 경우에도 `prev` 가 먼저 당겨진다.
결과는 항상 `desired` 이하이므로 안전 방향이다.

윈드업 억제를 노드가 아니라 이 함수 안에 두는 이유는 gtest 로 덮기 위해서다.
노드에 두면 순수 함수 테스트로 검증할 수 없다.

순수 함수이므로 `acc_core.hpp` 에 두고 gtest 로 덮는다. 상태(직전 목표속도와
시각)는 노드가 든다. 기존 22개 테스트와 같은 구조다.

### 2.4 파라미터 (`AccParams`)

```cpp
double accel_rate_limit  = 1.0;   // [m/s^2] 목표속도 상승률 한계
double rate_limit_windup = 2.0;   // [m/s] 실제속도보다 이만큼 이상 앞서지 않게
double rate_dt_max       = 0.5;   // [s] 한 스텝으로 인정하는 dt 상한
```

셋 다 `pnh.param` 으로 노출해 재빌드 없이 튜닝한다.

### 2.5 노드 상태 (`acc_planner.cpp`)

`prev_target_`, `prev_time_` 두 개를 든다. `run()` 의 마지막, 크루즈·앞차추종·곡률
제한을 모두 합산한 **뒤에** 한 번 적용한다. 목표가 어떤 이유로 오르든 동일하게
제한하기 위해서다.

```
dt = now - prev_time_
1. 시딩 : 첫 틱이거나 dt > rate_dt_max 면  prev_target_ = ego_vel
2. 적용 : target = rampTarget(prev_target_, target, ego_vel, dt, params_)
3. 저장 : prev_target_ = target, prev_time_ = now
```

**시딩이 필요한 이유** — 노드를 재시작하면 `prev_target_` 이 0 인데 차량은 달리고
있을 수 있다. 그대로 두면 0 을 명령해 급제동이 걸린다. 현재 속도로 시드한다.

**윈드업 억제가 필요한 이유** — 차량이 목표를 따라가지 못하는 상황(오르막, 제동
직후)에서 목표만 크루즈까지 달아나면, 차량이 회복되는 순간 그 격차만큼 급가속한다.
제한이 걸린 것처럼 보이지만 실제로는 무력화된 상태다. 실제 속도보다 2 m/s 이상
앞서지 못하게 묶는다.

## 4. 검증

같은 유턴 구간(idx 0~330)을 재주행해 현재 값과 비교한다.

기준값은 2026-07-29 주행 로그에서 취했다. 검증 도구는 `scripts/diag_tracker.py`
(읽기 전용, 초당 1회 기록)를 그대로 썼다. 두 주행 모두 크루즈 55km/h 조건이다.

시간 비용이 0.28초로 작은 이유는 커브 구간 자체가 곡률 제한으로 이미 저속이고,
상승률 제한은 탈출 이후의 가속만 늦추기 때문이다.

### 제한기 동작 직접 확인

노드 stdout 은 블록 버퍼링이라 프로세스를 kill 하면 로그가 유실된다. 로그가
비어 있는 것은 제한기가 동작하지 않았다는 증거가 아니다. `stdbuf -oL` 로
강제 플러시하고 `/target_velocity` 를 직접 관측해 확인했다.

```
1.4835 -> 2.7502 m/s  (1.2666초)
기울기 = 1.2667 / 1.2666 = 1.00006 m/s^2
[acc] rate limit: 15.28 -> 0.78 m/s
[acc] rate limit: 15.28 -> 2.82 m/s
```

목표는 15.28 m/s(55km/h)인데 출력이 정확히 `accel_rate_limit` 기울기로 눌려 나간다.

`accel_rate_limit` 은 1.0 으로 확정한다. 진동이 이미 제거되었고 시간 비용도
작으므로 0.5 로 낮출 이유가 없다.

### 남은 문제

최악 CTE 1.79m 는 차로 여유(차로 3.2m - 차폭 1.892m = 편도 0.65m)를 여전히
넘는다. 이는 이 과제의 범위 밖이다. 원인은 유턴 정점의 조향 포화이며(요구 조향
0.808 rad = 46.3도 vs `MAX_STEER` 0.65), 7절에 적은 대로 `MIN_LFD` 조정으로
별도 대응한다. 유턴 구간에서 `lfd` 가 4.0 에 고정되어 있으므로 이 구간에서
실제로 작동하는 파라미터는 `LFD_GAIN` 이 아니라 `MIN_LFD` 다.

## 6. 레퍼런스 비교 (erp42_racing_planning)

`~/Downloads/erp42_racing_planning`(ROS2 FOT 구현)에는 상승률 제한기가 없다.
문제가 구조적으로 발생하지 않는다.

| 기법 | 내용 | 우리 적용 |
|---|---|---|
| 다항식 궤적 | `QuarticPolynomial(s0, s0_dot, s0_ddot, s1_dot, 0.0, T)` — 현재 속도와 현재 가속도에서 출발해 T(3~5초)에 걸쳐 목표속도 도달. 속도·가속도 모두 연속(C2) | FOT 그 자체이므로 이식 불가. **본 설계의 rate limiter 가 이것의 1차 근사에 해당한다** |
| 저크 비용(`k_j`) | 상승률을 금지하지 않고 비싸게 만들어 부드러운 후보가 선택되게 함 | 목적이 같으므로 추가 불필요 |
| 좁은 속도 진폭 | CRUISE 에서 `v_max=5.5, v_min=3.0` (비율 1.83배) | 우리는 2.0~15.3 (7.6배). 유턴에서 15km/h 가 실제로 필요해 그대로 못 씀 |
| 선형 곡률-속도 매핑 | `calc_curvature_based_speed`: 카파 0.05 이하 v_max, 0.20 이상 v_min, 사이 선형 보간 | 우리 `sqrt(lat_accel_limit * R)` 은 물리적 근거가 있고 검증됨. 변경하지 않는다 |

주목할 점은 `_estimate_reference_curvature()` 가 **전방 20m 의 최대 곡률**을 쓴다는
것이다. erp42 도 앞만 본다. 커브 탈출 시 제한이 풀리는 구조는 우리와 같고, 다항식
궤적이 그 변화를 흡수하기 때문에 증상이 나타나지 않을 뿐이다.

이는 2.1 의 판단을 뒷받침한다. 커브 종료를 정교하게 판정하는 방향이 아니라,
목표속도 변화를 시간축에서 흡수하는 방향이 정공법이다.

### 남는 정밀도 차이

본 설계의 rate limiter 는 속도만 연속(C1)이다. 램프가 시작·종료하는 순간
가속도가 0 과 `accel_rate_limit` 사이를 계단으로 오간다. erp42 의 quartic 은
양끝 가속도가 0 이라 이 계단이 없다.

현재 문제(목표속도가 11 m/s 계단으로 상승)에 비하면 1.0 m/s^2 계단은 훨씬 작으므로
이번 범위에서는 다루지 않는다. 본 설계로 부족할 경우 다음 단계는 rate limiter 를
가속도까지 연속인 프로파일(S-curve 또는 quartic)로 올리는 것이다.
